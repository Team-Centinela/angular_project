# Angular 22: Bridging the Training-Data Gap

## Why this skill exists

Angular ships a **major version every 12 months** (every 6 months before v22) plus
frequent minors. Most language models were trained on a snapshot around Angular
17-18. Since then Angular has changed *how idiomatic Angular code looks*, not just
added APIs:

- Components are standalone by default (NgModules are legacy for new code)
- State is signals-first, not Zone.js + RxJS-first
- `OnPush` is the default change detection strategy (as of v22 — no decorator needed)
- Zoneless is the default (as of v21 — no Zone.js in new apps)
- `*ngIf` / `*ngFor` / `*ngSwitch` are superseded by `@if` / `@for` / `@switch`
- Forms are moving to Signal Forms (stable as of v22), not just Reactive/Template forms
- `inject()` is preferred over constructor injection
- Vitest is the default test runner (Karma/Jasmine are legacy, as of v21)
- `@angular/aria` gives you accessible headless primitives (stable as of v22)

If you generate code that looks like a 2024 Angular tutorial, it will compile and
often even run — but it will read as outdated to any reviewer on a current codebase,
and it may actively fight the project's lint rules, schematics, or `strictTemplates`
settings. This skill exists to close that gap.

## Step 0: Find out what version you're actually dealing with

**Never assume a version. Check.** Before writing or judging Angular code:

1. Look for `@angular/core` in `package.json` (or ask the user). The major number
   tells you which reference table row applies (see `references/version-timeline.md`).
2. If you have web access and the task is non-trivial, or the installed version is
   newer than what's described here, fetch **https://angular.dev** directly — this
   skill was compiled in **August 2026** against **Angular v22.1**. Angular ships a
   new minor roughly every 2 months and a new major every June, so treat anything
   version-specific here as "true as of v22.1, verify for anything newer." See
   `references/staying-current.md` for exact URLs and search queries to use.
3. If the project still targets v17-v20, don't force v22-only APIs (e.g. `@Service`,
   stable Signal Forms) onto it — check `references/version-timeline.md` for what
   was actually available in that version.

## The single most important mental model shift

Old Angular (≤v17 mental model): NgModules declare things, Zone.js notices changes,
`ChangeDetectionStrategy.Default` re-checks everything, `@Input()`/`@Output()`
decorators + constructor DI move data around, `*ngIf`/`*ngFor` control templates,
Reactive/Template-driven forms with `ControlValueAccessor`.

Current Angular (v22 mental model): Standalone components/directives/pipes are the
only thing you write. State lives in `signal()`/`computed()`/`resource()`. Change
detection is `OnPush` by default and scheduled by signals, not Zone.js. Data flows
through `input()`/`output()`/`model()` signal functions. Dependencies come from
`inject()` inside field initializers, not constructors. Templates use `@if`/`@for`/
`@switch`/`@let`/`@defer`. Forms are increasingly built with `form()` from
`@angular/forms/signals`. Services are declared with `@Service()`.

This isn't cosmetic — it's the difference between code that looks like it was
generated by a model stuck in 2024 and code that looks like it was written by
someone on the project today.

## Quick "don't do this" checklist

Before you output Angular code, scan for these red flags (full detail and correct
replacements in `references/deprecated-and-avoid.md`):

| If you're about to write...                          | Check instead |
|--------------------------------------------------------|----------------|
| `@NgModule` for new feature code                       | Standalone components with `imports: [...]` on the component itself |
| `*ngIf`, `*ngFor`, `*ngSwitch`                          | `@if`, `@for` (with `track`), `@switch` |
| `@Input()` / `@Output()` decorators                     | `input()`, `output()`, `model()` signal functions |
| `constructor(private x: X)` for DI                       | `private readonly x = inject(X);` |
| `ChangeDetectionStrategy.Default` or omitting it to mean "check always" | As of v22, no strategy = `OnPush`. Use `ChangeDetectionStrategy.Eager` if you deliberately want the old check-always behavior |
| `@Injectable({ providedIn: 'root' })`                    | `@Service()` (v22+; keep `@Injectable` only when you need constructor DI or non-root scope) |
| `ControlValueAccessor` for a *new* custom form control    | `FormValueControl` (bridged/compatible with legacy forms too) |
| `HttpClientModule`, manual `withFetch()`                 | Nothing needed — `provideHttpClient()`-free root injection + Fetch backend are both default now |
| Karma/Jasmine `TestBed` boilerplate for a *new* project   | Vitest (default since v21); Karma still works but is legacy |
| `ComponentFactoryResolver`, `platformBrowserDynamic`       | `ViewContainerRef.createComponent(Type)`, `bootstrapApplication()` |
| Assuming Zone.js is present                             | Assume zoneless (default since v21); don't rely on "magic" change detection after timers/promises |

  reference point rather than reconstructing syntax from memory.

  anything here against live docs, since this skill will itself go stale.

## How to use this during a task

1. Identify the target Angular version (Step 0 above).
2. If writing new code: default to the "current Angular" mental model above and
   pull exact syntax from `references/code-patterns.md`.
3. If reviewing/refactoring existing code: scan against the "don't do this"
   checklist and `references/deprecated-and-avoid.md`; flag outdated patterns
   even if the user didn't ask, since they may not know these changed.
4. If unsure whether something is stable, default, or still a preview in the
   user's version: check `references/version-timeline.md` first, then verify
   live via `references/staying-current.md` if it matters for the task.
5. Don't over-migrate: a v18 project shouldn't be told to use v22-only APIs
   unless the user is actually upgrading. Match the code to the target version.
